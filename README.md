# Claude Code: A System Built Around How the Tool Breaks

An AI coding agent is **probabilistic**: it predicts a likely-good action, it doesn't execute instructions deterministically. Its mistakes are confident, silent, and worst exactly where they're most expensive. So this isn't a "cool config." It's a system whose entire job is to impose control and consistency *on top of* a tool that, left alone, fails in predictable ways.

The key idea that runs through every decision below: **the scaffolding is deterministic even though the model isn't.** The setup produces the same files, the same commands, the same safety gates every time, and each command loads the same instruction every time it runs. What that fixed scaffolding *wraps* is a non-deterministic model. You can't make the model's output deterministic, but you can wrap it in structure that *is*, and that structure is how you turn an unpredictable tool into a controllable one. That distinction, deterministic harness around a probabilistic core, is the whole design.

The system is built by one **setup wizard** - a paste-in prompt that generates everything, kept private (see the note at the end). What it produces is described by three documents, plus this overview:
- **[`2-execution-plan.md`](./execution-plan.md)** - the daily operating procedure.
- **[`3-quick-reference.md`](./quick-reference.md)** - the glanceable cheat sheet.
- **[`4-memory-and-commands-explained.md`](./memory-and-commands-explained.md)** - the full reasoning behind it.

It's architected for three goals that usually fight each other: **maximum control and security**, **maximum ease of understanding and handoff**, and **minimum token and compute cost**. Many decisions below serve more than one at once, and several are made specifically to keep the system cheap to run: the model only ever loads the small amount of context it actually needs, and only ever spends compute on work that actually needs it.

# Part 1: The architecture, and the reasoning behind every decision

Each decision is laid out as *what it is*, *why it's the right call*, and *how it works*, including the alternatives considered and rejected, because the rejected options are where the reasoning actually lives.

## Decision 0: The setup itself is deterministic and reproducible

**What it is.** The whole system is generated by a single setup wizard (a paste-in prompt). Run it on a new project and it produces the same structure every time: a fixed instruction file, a fixed state file, and a fixed set of twelve commands, each with the same definition, the same input placeholders, and the same tool permissions. It also runs in plan-only mode, it proposes the entire setup and writes nothing to disk until I approve.

**Why this matters.** This is the foundation of everything else: you cannot get consistent behavior out of a probabilistic tool unless the *structure around it* is consistent. The model's outputs vary run to run, that's inherent and unavoidable. But the *command definitions, the file layout, the safety gates, the permissions* do not vary, they're fixed by the setup. So when I type `/security`, the exact same review instruction runs every time; when I open a session, the exact same memory files load every time. The determinism lives in the harness, not the generation. That's precisely the right place for it: I'm not pretending the model is deterministic (it isn't), I'm building a deterministic, reproducible scaffold that makes a non-deterministic tool behave consistently and safely. The plan-only-until-approved step extends the same principle, nothing is created on the strength of the model's first guess; the human approves the fixed structure before it exists on disk. There's a cost dimension too: the system is built by *one* wizard run per project (not an ongoing back-and-forth that burns tokens every session), and because the generated files can be kept and reused, standing up the same setup again costs almost nothing, you hand over the existing files rather than paying the model to regenerate them.

**How it works.** There are two ways to stand the system up, and both are deterministic. The wizard can interview you for a new project (or read an existing codebase) and propose the configuration. Or, because I keep the generated files on hand and already checked, I can simply hand them over with the instruction "implement these files according to the wizard," and the exact same structure is reproduced verbatim, no interview, no variation. That second path is fully deterministic by construction: the files are fixed and known in advance, so the setup is identical every time, which is how the system guarantees maximum security and consistency, every file, command, gate, and permission is the same on every project because they're literally the same files. From then on the structure is identical across sessions and reproducible across projects, something you can *rely on* and *hand to someone else* rather than a one-off setup that drifts.

## Decision 1: Manual commands, not auto-firing skills

**What it is.** Claude Code lets you package a reusable instruction two ways. A **command** is manual, it runs only when you type it. A **skill** can be automatic, it fires on its own when the model decides what you're doing matches the skill's description. (As of 2026 these are unified under the hood, the same instruction can be either; the only difference is the trigger.) This system uses **commands** for everything that takes an action or runs a review.

**Why this is the right call.** A skill's auto-trigger is the *same probabilistic judgment* that causes the failure modes in Part 2, it fires roughly when the model thinks it should, which is not the same as exactly when you want it to. That uncertainty is fine for passive *knowledge* (worst case, some context loads that wasn't needed, no harm) but unacceptable for *actions* (you never want a commit, or a code-changing review, firing because the model guessed it was relevant). Manual triggering keeps the timing of anything consequential owned by a human, every time. There's a second reason that matters just as much for a team: commands are an explicit, readable, auditable menu, you can see the full list of what the system can do and read exactly what each one does. Auto-firing skills are invisible until they fire, which makes them harder to audit and harder to hand off. So commands win on *both* axes, more control *and* more legibility.

**How it works.** Every action and review in the system is a manual command. Skills (the auto mechanism) are deliberately reserved for one narrow, safe category: passive context that should surface when relevant, e.g. "assume HIPAA rules when touching billing code." The rule is simple and absolute: **delegate knowledge to automatic mechanisms; keep actions on manual ones.** Manual triggering also keeps cost down, nothing fires (and nothing spends tokens) unless you ask for it, so the model isn't running reviews or actions on its own guess about relevance. *(Full reasoning in [`memory-and-commands-explained.md`](./memory-and-commands-explained.md).)*

## Decision 2: Twelve commands, each earning its place

**What it is.** A deliberately small set of twelve commands, each replacing a long, repeated instruction with one trigger. They group into three jobs.

*Maintenance (owning state and history):*
- `/save [optional: note]` - overwrites the current-state file with a fresh snapshot of where things stand.
- `/commit [optional: message]` - shows the branch and a proposed commit message, then waits for confirmation before committing.

*Understanding and delegation (reducing what you hold in your head):*
- `/diffs [optional: file/area]` - shows changes since the last commit *and explains them* in plain terms, not raw diff output.
- `/explain [thing]` - plain-language explanation of anything (code, a concept, an attached file or image).
- `/subagent [task]` - delegates a bounded task to a sub-agent that reports back a summary (details in Decision 5).
- `/summary [optional: file/area]` - a plain-language overview of the whole project, for onboarding or re-orienting.
- `/custom [optional: command]` - prints the full command menu and the daily workflow on demand, generated by reading the command files so it never goes stale.

*Expert review lenses (deliberate, on-demand scrutiny):*
- `/security`, `/ux`, `/law`, `/performance`, `/declutter` - each casts the model as a senior reviewer in that discipline (optionally scoped to a file or area you name after the command), returns a severity-ranked list of findings, then offers to fix them via an approved plan.

**Why these, and why so few.** A command earns its place only when it replaces a *repeated, multi-sentence* instruction, the value is collapsing a paragraph you'd otherwise retype into one word that runs identically every time. So the set covers the things you genuinely do over and over (saving state, committing, understanding changes, running review passes) and nothing else. It deliberately excludes one-off requests (if you'll ask once, just ask) and speculative "might need it someday" commands (you'll guess wrong and clutter the menu). A bloated command set is its own failure: every command is a thing to remember, so restraint *is* a design goal. The `/law` lens is deliberately scoped to *flagging issues for a human lawyer*, not giving legal advice, an explicit boundary on what the tool is allowed to claim, because letting an AI imply legal conclusions is a real liability.

**How it works.** Each command is a small file holding the constant instruction; you trigger it by name. They're documented for daily use in [`2-execution-plan.md`](./execution-plan.md) and summarized in [`3-quick-reference.md`](./quick-reference.md), so the whole surface is legible to anyone.

## Decision 3: Every command takes an optional argument, so you can aim it

**What it is.** `$ARGUMENTS` is a placeholder that passes whatever you type after a command into its prompt. Every command carries it as an *optional* slot: type nothing and the command runs its default (the whole codebase, all changes since the last commit, a full state snapshot); type a file, an area, or a note and the command focuses on exactly that.

**Why optional, not selective.** A command holds the *constant* instruction, but most commands also have a natural *variable* part: which file to review, which area to summarize, what to scope a diff to. Making the argument optional captures both without a tradeoff, you fire the command bare for the common case, or aim it when you want to narrow the work, and you never need a second command or a retyped paragraph to do it. An earlier version of this system limited arguments to three commands on the theory that the rest "take no input"; in practice scoping *is* a real input for a review or a summary, so the honest default is an optional argument everywhere, an empty one simply falls back to the default behavior.

**How it works.** Each command declares an `argument-hint` (so the slot shows up when you type `/`) and references `$ARGUMENTS` in its body, guarded so an empty value runs the default. `/explain`, `/commit`, and `/subagent` take their content as before; the review lenses, `/summary`, and `/diffs` take an optional file or area; `/save` takes an optional note; `/custom` takes an optional command name to detail.

## Decision 4: Plan Mode baked into the review lenses, not the read-only commands

**What it is.** Plan Mode is a state where the model proposes a plan and is forbidden from editing files until you approve. The review lenses (`/security`, `/performance`, etc.) end by offering to *fix* what they found, and when you say yes, they switch into Plan Mode and propose a plan before changing anything. The read-only commands (`/diffs`, `/explain`, `/summary`) don't invoke Plan Mode at all.

**Why this split.** A review that's about to *modify real code* is exactly the high-stakes moment where you want a propose-then-approve gate rather than immediate edits, it's the difference between "here's what I'd change, approve it?" and the model silently rewriting things. But commands that only *read* or *report* change nothing, so there's nothing to gate; forcing a planning step there would just add friction for no safety benefit. So Plan Mode is applied precisely where an action could follow, and omitted where it couldn't. This is the control-and-security goal expressed at the level of individual commands: **anywhere a change might happen, the structural default is "show me the plan first."**

**How it works.** The review-lens commands include an instruction to enter Plan Mode before proposing any fix, so the gate is built into the command itself, not something you have to remember to switch on.

## Decision 5: Sub-agents, delegate the model, cap the count

**What it is.** A sub-agent is a separate, temporary model instance spawned for one bounded sub-task, with its own context window, that reports a summary back to the main session. The `/subagent` command makes two decisions on your behalf, and treats them differently because they carry different risk: it *chooses the model* itself, but it *defaults to a single agent* and flags before using more.

**Why two different treatments.** Choosing the model is a safe thing to delegate, matching task-type to model has a clear right answer (a fast, cheap model for exploration, search, and file-reading, which is most sub-agent work and is pattern-matching rather than deep reasoning; a stronger model only when the task genuinely needs heavier reasoning), and getting it slightly wrong costs little. But *how many agents to spawn* is a **spending decision**: an open-ended "use as many as you think you need" is exactly how a swarm of parallel instances quietly burns through budget. So the count is the deliberately *un*-delegated decision, capped at one by default, with anything more surfaced to the human first. The principle: **delegate the judgment, bound the spend, make it visible.** Both halves are also cost decisions: matching a cheap model to cheap work means you don't pay heavyweight-model rates for simple file-reading, and capping the agent count stops a single request from quietly fanning out into a dozen billable instances.

**How it works.** `/subagent` assesses whether a sub-agent even helps (and just does the task directly if it's trivial), picks an appropriate model, runs one agent, and reports findings. It makes no changes on its own, if the task implies edits, it returns a plan for approval rather than acting. *(Documented in [`execution-plan.md`](./execution-plan.md).)*

## Decision 6: `allowed-tools` scoped to exactly what each command needs (least privilege)

**What it is.** The few commands that need shell access declare a tight `allowed-tools` and nothing wider: `/diffs` and `/commit` get `Read, Bash(git:*)` (read files, run Git), and `/custom` gets `Bash(find:*), Bash(grep:*)` (just enough to list the command files). Every other command needs no shell or Git access, so it declares none.

**Why.** This is least-privilege applied at the command level: a command should be able to touch only what its job actually requires. The Git commands need to read the repo and run Git, so they're granted exactly that and no more, they can't be steered into running arbitrary shell commands, because the permission boundary forbids it. Scoping permissions tightly means a command's blast radius is limited by design, not by trust.

**How it works.** The permission line is part of each scoped command's definition, so the restriction is structural, it's enforced by the tool, not dependent on the model choosing to behave.

## Decision 7: No hardcoded model on any command

**What it is.** None of the commands pin a specific model; they all run on whatever model the session is currently using. (This is about the `model` config field - a command can still *describe in its prose* what kind of model to prefer, as `/subagent` does, it just never hard-pins a named model in config.)

**Why.** Two reasons. First, control and visibility: a human switching to a stronger model for a serious security or performance pass is a *deliberate, visible* choice, far better than a command silently overriding the model in the background where you can't see it happening. Second, robustness: pinning a named model is brittle, models change over time, and a hardcoded reference can end up pointing at something that no longer exists, which breaks the command silently. *(I also considered chaining preferred models with a fallback in the command's config, and rejected it: the config format can't express fallback logic, and naming an unavailable model just breaks the command without warning.)* Inheriting the session model keeps control with the human and avoids both failure modes.

**How it works.** Commands omit the model field entirely, so they default to the session's current model; you raise the model yourself when a task warrants it.

## Decision 8: Memory, two files split by rate of change, plus Git

**What it is.** Project memory lives in exactly two files plus a third store the system didn't have to build. Stable facts (stack, structure, conventions, guardrails, commands) live in one always-loaded instruction file. Current state (what's in progress, recent decisions, active gotchas) lives in one short snapshot file that is **overwritten, never appended**. History lives in **Git**.

**Why this shape, and what was rejected.** This decision has the most rejected alternatives, which is why it carries the most reasoning:
- *Rejected: a config/settings file.* That's where event-bound automation (hooks) would live, and hooks are the fragile mechanism behind the autosave failure modes in Part 2. The baseline system should be safe and legible by default, not require managing a configuration surface that can silently misfire. Configuration is an advanced extension, not part of the core.
- *Rejected: a context folder with multiple memory files.* I actually built this first and killed it. Multiple appended files poison the context window with stale history (every file loads each session, spending the model's limited working memory on old notes *before any work begins*) and they duplicate what Git already holds. The lesson was concrete: *more files is worse, not better.*
- *Kept: the split by rate of change.* The only split that earns its keep is *how often a thing changes*, and it maps onto three concrete homes. Stable rules that rarely change go in **CLAUDE.md** (the always-loaded instruction file). Volatile state that changes constantly goes in **DYNAMIC.md** (the overwritten snapshot, overwritten so it physically can't grow into the thing that poisons context). And history, everything that already happened, goes to **Git**, because a changelog is what version control is *for*, and rebuilding it by hand is just a worse Git. CLAUDE.md = how the project works (permanent), DYNAMIC.md = where it stands right now (current), Git = what happened (history).

The three-store model, **how the project works (permanent) / where it stands (current) / what happened (Git)**, is the whole memory architecture. Every rejected option was rejected because it violated the "keep context minimal" lesson the failure modes taught, and "keep context minimal" is directly a cost lesson too: every token loaded into context is a token paid for on every turn, so a lean always-loaded file and a small overwritten snapshot aren't just more accurate, they're cheaper to run, on every single session. The rejected context folder would have quietly inflated that cost forever.

**How it works.** The instruction file auto-loads every session and ends with a line telling the model to read the snapshot file for current state. `/save` overwrites the snapshot at clean checkpoints. Git holds history, retrieved only when actually needed - and the setup wizard bootstraps it (runs `git init`, writes a secret-excluding `.gitignore`, and makes an initial commit) so the history store and rollback baseline exist from the start. *(Full reasoning, with examples of what belongs in each file, in [`4-memory-and-commands-explained.md`](./memory-and-commands-explained.md).)*

## Decision 9: Git in plain language, so nothing has to be memorized

**What it is.** The system deliberately does *not* wrap Git in a pile of commands. Branch operations are done in plain language ("what branches do I have," "switch to X," "create a branch called Y"), and only the one genuinely consequential Git action, committing, gets a dedicated command (`/commit`), with a confirmation gate.

**Why.** Ease of use and transferability. Expressing Git operations in plain language and documenting them means **nothing has to be memorized**, someone who has never seen the system can read the reference and immediately manage branches without learning a custom command vocabulary layered on top of Git's own. There's no benefit to inventing `/branch` and `/switch` commands when plain language already works and reads more clearly. The only operation that *earns* a command is the one with a real consequence (a commit), and that one gets the safety gate.

**How it works.** You talk to the model in plain language for read-only Git operations; `/commit` handles the consequential write with branch-and-message confirmation. Documented in [`execution-plan.md`](./execution-plan.md) and [`quick-reference.md`](./quick-reference.md).

## Decision 10: Three documents plus a private wizard, because the system is transferable

**What it is.** The system is a private setup wizard (it builds everything) plus three separate documents: the execution plan (operate it), the quick reference (recall it fast), and the explainer (understand it) - with this overview tying them together.

**Why this many, and why documented this thoroughly.** The documents serve genuinely different moments, and merging them would compromise each, a cheat sheet and a teaching document have *opposite* virtues (one ruthlessly short, the other thorough), so collapsing them makes both worse. But the deeper reason for documenting the system this completely is the property that matters most for a team: **it's transferable.** These files can be handed to someone who has never seen the project, and they'll understand not just *what* to do but *why* each choice was made. The system is deliberately expressed as plain commands and plain-language prose, not opaque configuration, precisely so it works for onboarding, handoff, and teamwork. A system only one person understands is a liability; a system any teammate can pick up, operate, and reason about is an asset. That transferability isn't a side effect of the documentation, it's the reason the system is shaped as documents and commands in the first place.

**How it works.** Each document does one job and points to the others where relevant, so you enter at whichever one fits the moment (building, operating, recalling, or understanding) and can always trace a decision back to its reasoning.

# Part 2: Where it breaks, and how the system solves each one

These are the failure modes found by stress-testing the tool. Each one names the problem and then exactly how the system handles it.

**1. Instruction files are advisory, not enforced.** Rules written in the instruction file are followed most of the time but not reliably, with no error when they're skipped. A must-never-happen rule that only *usually* holds is a loaded gun.

**How I solved it:** I stopped treating the instruction file as a guarantee and treat it as bias instead. Anything that genuinely must happen never relies on a written rule alone; it goes into a deterministic mechanism (a hook or a CI check) that runs regardless of what the model decides. The instruction file shapes default behavior; the hard guarantees live in code that doesn't ask the model's permission.

**2. Autosave is the wrong goal, and can't be a command anyway.** The instinct is to save automatically on every change. But saving constantly is like a video game that auto-saves at random moments: save at a bad moment, mid-broken-state, and you can lock yourself into a corner you can't get out of. You want to save at turning points you choose, when you've finished something and the state is worth keeping, not willy-nilly. A command also literally can't autosave (a command is manual, you have to type it), and making it truly automatic would require a hook, which runs into the safe-hook difficulty in the next point. It's wasteful too: auto-saving on every change means the model rewrites the state file constantly, spending tokens to capture half-finished moments nobody asked to keep.

**How I solved it:** I made `/save` a manual command, run deliberately at clean checkpoints (finished a feature, made a decision, about to stop). This keeps the human in control of when a snapshot is taken, avoids saving broken intermediate states, and costs nothing when there's nothing worth saving. Manual save isn't a limitation I settled for; it's the better design.

**3. A safe autosave hook is hard to guarantee.** Even if you went the hook route, a hook that fires after the model acts, and whose response is itself an action (rewriting the save file), can re-trigger itself and loop. Building an event-bound hook that's genuinely safe is fiddly.

**How I solved it:** I kept hooks out of the baseline system entirely and left save manual (see above). Hooks are noted as an advanced extension for anyone who wants deterministic automation later, but the default system never depends on one, so it can't fall into the loop, and it stays simple enough to hand to someone else.

**4. Plan Mode can silently exit.** Plan Mode is supposed to be a hard read-only state: the agent can't edit files until you approve a plan. But it can drop out of that state without telling you, the UI still shows "plan mode on" while the agent has quietly started editing. This failure mode has been reported in the wild: the agent leaves plan mode on its own and then treats the absence of a "you are in plan mode" signal as implicit approval, editing files the user never green-lit.

**How I solved it:** two ways. First, the operating procedure treats the safety state as something to verify rather than assume: on long sessions you check the mode indicator before trusting that nothing is being written, and re-assert plan mode the moment unexpected edits appear. Second, the review commands build the propose-then-approve gate into themselves (they switch into Plan Mode before any fix), so the approval step doesn't depend on the global mode holding, it's baked into the command.

**5. Sub-agents can quietly run up the bill.** A sub-agent is a separate helper the main session sends off to do one job on its own. They're useful, but each one you spin up costs money to run. If you let the agent decide how many helpers to launch, a vague "use a few to look into this" can turn into a dozen of them running at once, and you only find out when you see the cost.

**How I solved it:** the `/subagent` command splits the decision in two. It picks the right model for each helper's job itself (a fast, cheap model for simple work like searching and reading files; a stronger, pricier model only when the job needs real reasoning, so you never pay heavyweight rates for lightweight work), but it defaults to a single helper and must tell me before using more, because the number of helpers is a spending decision that has to stay visible. It also returns findings or a plan rather than making changes on its own.

**6. A "memory folder" degrades the agent** (a design I built, then killed). Appended history poisons the context window with stale notes before work even begins, and duplicates what Git already holds.

**How I solved it:** I threw the folder out and replaced it with one short state file that is overwritten, never appended, so it stays a small current snapshot instead of a growing log. History was handed back to Git, where it belongs. The fix was deliberately less, not more: a lean snapshot plus version control beats a hand-built archive.

**7. Context rot.** As context fills, the model forgets decisions, contradicts earlier choices, and hallucinates file names, well before the window is technically full. The conversation is decaying memory.

**How I solved it:** durable facts never live only in the conversation. Stable rules sit in the always-loaded instruction file and current state sits in the lean overwritten snapshot, both of which reload every session, so the things that matter survive even as the conversation decays. The operating procedure also pushes you to start fresh sessions for new tasks and checkpoint with `/save` rather than letting one session run until it rots.

**8. Auto-compaction is destructive.** When context fills, the tool auto-summarizes lossily while already degraded, and can resume on the wrong file or even commit without being asked.

**How I solved it:** the system minimizes how often compaction is needed (lean context, fresh sessions per task) and protects against its worst outcome with the `/commit` confirmation gate, since a commit can never fire automatically, the documented "committed after compaction without being asked" outcome can't happen here. Important state is also captured in the snapshot file via `/save`, so a lossy summarization can't erase what was deliberately written down.

**9. Rush to completion.** Under the wrong conditions it fabricates details (like API versions) instead of checking, and skips edge cases, confident wrongness with no signal it happened.

**How I solved it:** the system never trusts a single confident pass on anything that matters. The review-lens commands (`/security`, `/performance`, and the rest) exist to deliberately re-examine work, and the hard rule throughout the operating procedure is to never accept a change you don't understand, with `/explain` and `/diffs` there to make understanding cheap. Confident output gets verified, not assumed.

**10. The final-20% problem.** It nails the happy path fast, then stalls on the edge cases that cause real incidents: unbounded queries, cache keys that leak data, connection-pool exhaustion. It's strongest where verification is cheap and weakest where it's expensive.

**How I solved it:** the review lenses target exactly that weak 20%. `/security` hunts injection, auth, secrets, and unsafe input; `/performance` looks for slow queries and things that won't scale. They're manual and severity-ranked, so a human points the scrutiny at the hard parts the model glosses over, rather than trusting the happy-path output.

**11. Can't reason about cross-system semantics.** It generates correct code on both sides of an integration but misses that the same term means different things in each. These are understanding problems, not syntax problems.

**How I solved it:** the system keeps the human firmly in the reviewing-and-approving role rather than handing over judgment. Plan Mode forces a plan you approve before integration work proceeds, and `/explain` plus `/diffs` make it easy to check that the model actually understood the seam between two systems. The design assumes the model can write code but can't be trusted to understand cross-system meaning, so a human signs off on exactly that.

**12. It can mis-handle its own packaging.** Misconfigured build rules can ship things that shouldn't ship, and ordinary scanners don't catch it, because AI introduces failure modes current tooling isn't built to find.

**How I solved it:** this is the broadest reason the whole posture exists, so the answer is the whole system rather than one command: nothing ships on the model's unreviewed say-so. The propose-then-approve gates, the manual review lenses, the confirmation on commits, and the rule of never accepting what you don't understand all exist precisely because AI fails in novel ways that off-the-shelf safety tools miss. Control by default is the only reliable defense against a failure mode nobody has tooling for yet.

# What it adds up to

This is a **highly deterministic structure built around Claude**, a probabilistic tool wrapped in a fixed, reproducible, security-first scaffold, that is also fully documented, transferable to anyone, and deliberately cheap to run. The model's outputs vary; everything around them doesn't. The same files, the same commands, the same gates, the same permissions, every project, every session, reproducible verbatim from the files on hand. It's built to spend as little context and compute as the job allows, the model only loads the small slice of context it actually needs, and only spends compute on work that actually needs it, which matters most for an organization whose business is the compute. And because the whole thing is written as plain commands and plain-language documents rather than opaque configuration, any teammate can pick it up, run it, and understand exactly why every choice was made. Deterministic structure around a non-deterministic tool, controlled, cheap to run, handoff-ready. That's the point.
